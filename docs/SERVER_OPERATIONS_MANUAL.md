## 1. Server Directory Layout & Volume Mounts

On `dblub` (`postgres`), Docker containers run the ETL ecosystem and mount host directories from `/opt/ETL/`:

| Host Path on `dblub` | Container Mount Point | Why This Directory Exists |
|:---|:---|:---|
| `/opt/ETL/spark/jobs/pyspark_pipeline/` | `/opt/spark/jobs/pyspark_pipeline/` | **Live PySpark ETL Application:** Python code, configs, migrations, and scripts executed by Spark Connect and CLI runs. |
| `/opt/ETL/airflow/dags/` | `/opt/airflow/dags/` | **Active Airflow DAGs:** The standalone folder scanned continuously by `airflow-scheduler` to discover and schedule DAGs. |
| `/opt/ETL/airflow/dags-config/` | `/opt/airflow/dags-config/` | **Airflow YAML Configs:** Source tags, schedules, priority definitions. |
| `/opt/ETL/airflow/logs/` | `/opt/airflow/logs/` | **Airflow Task Logs:** Real-time log outputs generated by running tasks. |
| `/opt/ETL/shared/data/local_dev/` | `/opt/shared/data/local_dev/` | **Data Lake Storage:** Raw Landing Parquet (`landing/`) and Silver Delta tables (`history/`). |
| `/tmp/data_pipeline/` (or `/home/dbl/data_pipeline/`) | *(Host only)* | **Git Working Clone (Staging Area):** Where code is pulled from GitLab before copying to `/opt/ETL`. |

### Why We Use a Staging Clone (`/tmp` or `/home/dbl`) Instead of Running Git in `/opt/ETL`
Docker containers run with different Linux User IDs (`airflow` is UID 50000, `spark` is UID 1000, host is UID 0 `root`). These containers write temporary files, cache files (`__pycache__`, `.pytest_cache`), and logs inside `/opt/ETL`. If `/opt/ETL` were a direct Git clone, running `git pull` would constantly fail with dirty working tree errors, file lock collisions, and permission conflicts. The staging clone isolates Git operations from Docker runtime writes.

## 2. Code Deployment & Git Synchronization (Detailed Breakdown)

Run this sequence on `dblub` (Linux shell as `root`) after pushing new code or fixes from your workstation:

```bash
# === RUN THESE COMMANDS ON root@dblub ===

# 1. Switch to the git repository staging folder
cd /tmp/data_pipeline

# 2. Align branch and pull latest changes from GitLab
git checkout erp_landing
git pull origin erp_landing

# 3. Copy updated PySpark ETL code into the live Docker volume
cp -r /tmp/data_pipeline/spark/jobs/pyspark_pipeline/* /opt/ETL/spark/jobs/pyspark_pipeline/

# 4. Copy updated Airflow DAG definitions into the live Airflow DAG volume
cp -r /tmp/data_pipeline/spark/jobs/pyspark_pipeline/dags/* /opt/ETL/airflow/dags/

# 5. Copy DAG YAML configurations (silently skips if absent)
cp -r /tmp/data_pipeline/airflow/dags-config/* /opt/ETL/airflow/dags-config/ 2>/dev/null || true

# 6. Set open read/write/execute permissions for Docker container users
chmod -R 777 /opt/ETL/spark/jobs/pyspark_pipeline/
chmod -R 777 /opt/ETL/airflow/dags/
```

### What Each Deployment Command Is Doing:

| Command | Deep Dive: What It Does & Why It Is Executed |
|:---|:---|
| `cd /tmp/data_pipeline` | **Change Directory:** Navigates the Linux bash shell to the local Git repository working folder. If you try to run `git pull` from `/root`, `/tmp`, or `/home/dbl`, Git will abort with `fatal: not a git repository`. |
| `git checkout erp_landing` | **Select Branch:** Ensures the Git clone is pointing to the active development branch (`erp_landing`) so you don't pull into `main` or `master` by mistake. |
| `git pull origin erp_landing` | **Download Updates:** Connects over HTTP to GitLab at `postgres:8929`, fetches all newly pushed commits, compares them against the local clone, and fast-forwards/merges the local files. Prompts for username/password if credentials are not cached. |
| `cp -r /tmp/data_pipeline/spark/jobs/pyspark_pipeline/* /opt/ETL/spark/jobs/pyspark_pipeline/` | **Deploy ETL Application:**<br>• `cp`: Standard Linux copy program.<br>• `-r` (*recursive*): Copies all files and subdirectories (`src/`, `config/`, `jobs/`, `utils/`, `migrations/`).<br>• `/*`: Wildcard matching all contents within the staging directory.<br>• Destination: `/opt/ETL/spark/jobs/pyspark_pipeline/`, which is the exact host directory mapped directly into the Spark Connect container. |
| `cp -r /tmp/data_pipeline/spark/jobs/pyspark_pipeline/dags/* /opt/ETL/airflow/dags/` | **Deploy Airflow DAGs:** Copies the standalone Python DAG definition scripts (e.g. `00_master_pipeline.py`, `05_medallion_source_erp_db.py`) into Airflow's active DAG root. Airflow scheduler detects and parses these files automatically. |
| `cp -r .../dags-config/* ... 2>/dev/null \|\| true` | **Safe Optional Copy:**<br>• `2>/dev/null`: Redirects standard error (file not found or directory empty) to `/dev/null` (silences errors).<br>• `\|\| true`: If the copy command exits with a non-zero code, `true` returns exit code 0, preventing terminal scripts from aborting. |
| `chmod -R 777 /opt/ETL/spark/jobs/pyspark_pipeline/` | **Permission Normalization:**<br>• `chmod`: Changes file read/write/execute mode bits.<br>• `-R` (*recursive*): Recursively traverses every subfolder and file.<br>• `777`: Grants Read (4) + Write (2) + Execute (1) = 7 to Owner, Group, and Others (`rwxrwxrwx`).<br>• **Why critical:** When you run `cp` as `root`, Linux marks files owned by `root:root` with default `755` or `644`. When the Airflow container (UID 50000) or Spark container (UID 1000) attempts to create lock files, write logs, or compile `.pyc`, it crashes with `PermissionDenied: [Errno 13]`. `777` prevents this. |
| `chmod -R 777 /opt/ETL/airflow/dags/` | **DAGs Permissions:** Ensures Airflow's DAG-parser process (UID 50000) has full rights to inspect and execute the DAG scripts. |

## 3. ETL Execution Commands (`jobs/app_etl.py` Detailed Breakdown)

`jobs/app_etl.py` is the central orchestrator CLI for the PySpark ETL platform. All commands below are run from inside `/opt/ETL/spark/jobs/pyspark_pipeline`:

```bash
cd /opt/ETL/spark/jobs/pyspark_pipeline
```

### Command Flags Reference Table

| Flag | Argument Type | What It Does & How the Engine Uses It |
|:---|:---|:---|
| `--source_tag` | `string` (e.g. `source_erp_db`) | **Source System Identifier:** Reads connection credentials and parameters from `config/databases.ini` and `metadata.db_sources`. Filter queries to tables belonging to this source. |
| `--action` | `string` (`run_pipeline`, `run_landing`, etc.) | **Pipeline Action:** Defines which execution phase or operational maintenance function to execute. |
| `--priority` | `integer` (`1`, `2`, `3`) | **Execution Priority Batch:** Filters tables registered in `metadata.db_tables_etl` by their priority level. Priority 1 tables are core, high-frequency tables. |
| `--table` | `string` (e.g. `tbltaskassignment`) | **Targeted Single Table:** Runs only this specific table. **Crucial:** Passing `--table` automatically bypasses daily skip checks (`is_active` / `last_run` filters) and forces immediate processing. |
| `--target_tag` | `string` (e.g. `eland`, `pgdbbi`) | **Target Warehouse Profile:** Overrides the destination warehouse tag, allowing writes to be routed to alternative database schemas. |
| `--run_id` | `UUID string` | **Execution Identifier:** Pinpoints an exact pipeline execution run in `metadata.etl_job_runs` for status querying or governed execution. |
| `--operation` | `string` (`status`, `reset_watermark`, etc.) | **Sub-Operation for `fix`:** Specifies the maintenance action to perform. |
| `--dry-run` | Flag (no argument) | **Simulation Mode:** Inspects catalogs, compares schemas, and prints planned actions without writing data or updating metadata. |

---

### 3.1 End-to-End Pipeline Runs (`--action run_pipeline`)

Executes the complete three-tier medallion architecture in sequence:  
**Landing (Bronze: JDBC $\to$ Parquet)** $\to$ **History (Silver: Deduplication + Delta)** $\to$ **Target (Gold: CDC MERGE / UPSERT)**.

```bash
# 1. Run all Priority 1 tables for source_erp_db
python jobs/app_etl.py --source_tag source_erp_db --action run_pipeline --priority 1
```
*What it does:* Connects to the `source_erp_db` database, queries `metadata.db_tables_etl` for active Priority 1 tables, checks if they ran today (skips if already completed), pulls incremental rows via JDBC, writes Bronze Parquet, validates schemas and deduplicates into Silver Delta, and executes MERGE/UPSERT into Gold.

```bash
# 2. Force-run a single table (Bypasses daily skip check!)
python jobs/app_etl.py --source_tag source_erp_db --action run_pipeline --priority 1 --table tbltaskassignment
```
*What it does:* Targets only `tbltaskassignment`. Ignores previous daily completion locks and processes the table end-to-end through Bronze, Silver, and Gold.

```bash
# 3. Run a single table writing to a custom target database tag (e.g. eland)
python jobs/app_etl.py --source_tag source_erp_db --action run_pipeline --priority 1 --table tbltaskassignment --target_tag eland
```
*What it does:* Same as above, but explicitly routes the Gold layer UPSERT into the database defined under the `eland` connection profile in `config/databases.ini`.

---

### 3.2 Individual Medallion Layer Runs

Use these commands when testing or rerunning a specific layer in isolation:

```bash
# Bronze Only: Extracts from JDBC source to Landing Parquet storage
python jobs/app_etl.py --source_tag source_erp_db --action run_landing --priority 1
python jobs/app_etl.py --source_tag source_erp_db --action run_landing --priority 1 --table users
```
*What it does:* Connects to source JDBC, reads incremental data based on watermark, creates a source snapshot, and saves it into `/opt/ETL/shared/data/local_dev/landing/<source>/<table_name>/`. Does NOT update Silver or Gold.

```bash
# Silver Only: Reads Bronze Parquet, checks schema drift, deduplicates, writes Delta
python jobs/app_etl.py --source_tag source_erp_db --action run_history --priority 1
python jobs/app_etl.py --source_tag source_erp_db --action run_history --priority 1 --table users
```
*What it does:* Reads raw Bronze files, applies schema casting, routes invalid rows to quarantine, and executes Delta Lake append/merge into `/opt/ETL/shared/data/local_dev/history/<source>/<table_name>/`.

```bash
# Gold Only: Reads Silver Delta, tracks CDC changes, and writes to analytical warehouse
python jobs/app_etl.py --source_tag source_erp_db --action run_target --priority 1
python jobs/app_etl.py --source_tag source_erp_db --action run_target --priority 1 --table users
```
*What it does:* Reads the Silver Delta table, validates business keys, generates UPSERT statements, commits rows to the target analytical warehouse (e.g. PostgreSQL `eland`), and updates the CDC watermark in `metadata.table_cdc_state`.

---

### 3.3 Governed Execution Mode (`--action run_governed`)

```bash
python jobs/app_etl.py --action run_governed --run_id 1a8f8f55-c03b-48e6-afa1-ba32b5c51bad
```
*What it does:* Loads an immutable execution contract from `metadata.etl_job_runs` matching `--run_id`. Guarantees that exact table lists, schema versions, and parameter snapshots are replayed identically. This is the mode triggered by the Streamlit GUI.

## 4. Emergency Fix & Maintenance Commands (`--action fix`)

The `fix` action provides CLI operations to inspect and repair state without requiring manual SQL queries against the metadata database.

### 4.1 Check Pipeline Run Status & Error Traceback

```bash
python jobs/app_etl.py --action fix --run_id 2287018c-ffff-4942-9be7-e4ca13728917 --operation status
```
*What it does:* Queries `metadata.etl_job_runs` and `metadata.batch_log` for the specified run UUID. Prints the execution start time, duration, completion status (`SUCCESS`, `FAILED`, `ABORTED`), affected row counts, and the exact Python exception traceback if it failed.

---

### 4.2 Query / Inspect Current CDC Watermark

```bash
python jobs/app_etl.py --source_tag source_erp_db --action fix --table ptblusertype --operation check_watermark
```
*What it does:* Reads `metadata.table_cdc_state` for `ptblusertype` and displays:
- `last_watermark_ts`: The highest timestamp committed during the last successful run.
- `last_watermark_val`: Numeric sequence / ID watermark (if applicable).
- Compares the watermark against the current system time to detect if the watermark is set in the future.

---

### 4.3 Reset Stuck or Poisoned CDC Watermarks

```bash
python jobs/app_etl.py --source_tag source_erp_db --action fix --table ptblusertype --operation reset_watermark
```
*What it does:* Safely sets `last_watermark_ts` to `NULL` (or epoch `1970-01-01 00:00:00`) in `metadata.table_cdc_state`.  
**When to use:** Resolves `[CDC_SOURCE_CURSOR_REGRESSION]` errors when a watermark was accidentally advanced into the future (e.g. due to UTC vs PKT timezone offsets). On the next run, the pipeline will extract from baseline without errors.

---

### 4.4 Force-Clear Daily Run Lock (`operation rerun`)

```bash
python jobs/app_etl.py --source_tag source_erp_db --action fix --table ptblusertype --operation rerun
```
*What it does:* Clears the daily completion flag in `metadata.table_execution_state` for this table. Allows the table to be picked up again in automated batch runs on the same day without waiting for tomorrow's schedule.

---

### 4.5 System Healthcheck

```bash
python jobs/app_etl.py --action healthcheck
```
*What it does:* Executes a comprehensive 4-point diagnostic probe:
1. **Metadata Database:** Tests read/write access to PostgreSQL `pgdbbi`.
2. **Schema Certification:** Verifies all 48 database migrations are applied and match hash checksums.
3. **Source Connections:** Validates TCP and authentication reachability for all sources in `config/databases.ini`.
4. **Spark Connect:** Probes `sc://postgres:15002` to confirm the Spark Connect server is accepting client sessions.

---

### 4.6 Schema Crawler & Catalog Synchronization (`--action sync`)

```bash
# Dry run: Discovers tables without saving
python jobs/app_etl.py --source_tag source_erp_db --action sync --dry-run

# Live run: Saves newly discovered tables into metadata
python jobs/app_etl.py --source_tag source_erp_db --action sync
```
*What it does:* Introspects the source database's `INFORMATION_SCHEMA` or system catalog. Identifies newly created tables, altered column types, or dropped columns, and registers them into `metadata.db_tables_etl` and `metadata.db_columns_etl`.

### 5.3 Streaming Live Airflow Task Logs

Airflow writes task execution logs directly to `/opt/ETL/airflow/logs/`:

```bash

```
*What each part does:*

- `-n 100`: Shows the last 100 lines immediately upon running.
- `-f` (*follow*): Keeps the terminal open and prints new log entries as they are generated by the worker. Press `Ctrl+C` to exit.

## 7. Quick Incident Recovery Runbook

### Scenario 1: `[CDC_SOURCE_CURSOR_REGRESSION]` Error
**Error Signature:** `Source maximum timestamp '2026-10-15 16:16:45' is behind committed watermark '2026-10-15 21:16:45'`.  
**Root Cause:** A run executed from a local workstation running in local time (`PKT` = UTC+5) stamped the metadata with a timestamp 5 hours ahead of the server's UTC clock.  
**Resolution Steps:**
1. Navigate to the pipeline directory on `dblub`:
   ```bash
   cd /opt/ETL/spark/jobs/pyspark_pipeline
   ```
2. Reset the watermark for the affected table:
   ```bash
   python jobs/app_etl.py --source_tag source_erp_db --action fix --table <table_name> --operation reset_watermark
   ```
3. Re-trigger the table or DAG. The table will safely reload without cursor regression.

---

### Scenario 2: `Schema drift detected. Found X critical changes.`
**Error Signature:** `Silver failed for temp: Schema drift detected.`  
**Root Cause:** A column data type was modified in the source database (or Spark JDBC inferred Oracle `FLOAT(126)` as `DecimalType(38,10)`).  
**Resolution Steps:**
1. Ensure `src/validation/schema_classifier.py` includes safe widening:
   ```python
   FLOAT: ["DECIMAL", "STRING"],
   DECIMAL: ["FLOAT", "STRING"],
   ```
2. Open the Streamlit GUI (`http://postgres:8501`), navigate to **Operations** $\to$ **Schema Drift Alerts**, review the change, and click **Approve / Resolve Drift**.
3. Or manually align `metadata.db_columns_etl`:
   ```sql
   UPDATE metadata.db_columns_etl 
   SET canonical_type = 'DECIMAL' 
   WHERE table_id = <table_id> AND source_column = '<column_name>';
   ```

---

### Scenario 3: `fatal: not a git repository`
**Error Signature:** `fatal: not a git repository (or any of the parent directories): .git`  
**Root Cause:** Running `git pull` from `/root`, `/tmp`, or `/home/dbl` instead of inside the directory containing the `.git` folder.  
**Resolution Steps:**
```bash
# Navigate to the clone first:
cd /tmp/data_pipeline
# (or cd /home/dbl/data_pipeline)
git pull origin erp_landing
```

---

### Scenario 4: Downstream Sources Marked `upstream_failed` (Orange) in Airflow
**Error Signature:** Source 1 failed, causing Sources 2 through 7 to turn orange and skip execution.  
**Root Cause:** The DAG task trigger rule was default `all_success`.  
**Resolution Steps:**
1. Verify [`dags/00_master_pipeline.py`](file:///c:/Users/Administrator/Pictures/landing_pipeline/data_pipeline/spark/jobs/pyspark_pipeline/dags/00_master_pipeline.py) specifies `trigger_rule="all_done"`.
2. Sync the DAGs folder:
   ```bash
   cp /tmp/data_pipeline/spark/jobs/pyspark_pipeline/dags/* /opt/ETL/airflow/dags/
   chmod -R 777 /opt/ETL/airflow/dags/
   docker restart airflow-scheduler
   ```
3. Re-trigger `00_master_pipeline`. Each source will now execute independently regardless of whether other sources passed or failed.
